# Message Structure Definition - Summary

## Overview

Implemented the Phoenix Channels message structure with comprehensive support for all message types. The `PhoenixMessage` struct accurately represents the Phoenix V2 protocol's 5-field message format: `[join_ref, ref, topic, event, payload]`.

## Task Requirements

### ✅ 1.2.1.1 Define PhoenixMessage struct with 5 fields matching protocol spec

Implemented `PhoenixMessage` struct with all required fields:

```zig
pub const PhoenixMessage = struct {
    join_ref: ?[]const u8,        // Required for phx_join, null otherwise
    ref: ?[]const u8,              // Unique message reference
    topic: []const u8,             // Channel topic
    event: []const u8,             // Event name
    payload: std.json.Value,       // JSON object payload
    allocator: std.mem.Allocator,  // Memory management
};
```

**Key Design Decisions:**
- `join_ref` and `ref` are nullable (`?[]const u8`) as they're not always required
- `topic` and `event` are non-nullable as they're always present
- `payload` uses `std.json.Value` to support arbitrary JSON structures
- Includes `allocator` field for memory management consistency

### ✅ 1.2.1.2 Implement field types (nullable strings, JSON value for payload)

**Field Type Implementation:**
- **Nullable fields**: Used `?[]const u8` for `join_ref` and `ref`
- **Required fields**: Used `[]const u8` for `topic` and `event`
- **Payload**: Used `std.json.Value` which can represent any JSON type
- **Allocator**: Stored for consistent memory management

**Phoenix Protocol Requirements:**
- `join_ref`: Required only for `phx_join` events
- `ref`: Should be unique per socket (generated by RefCounter)
- `topic`: Special meaning for "phoenix" (heartbeat topic)
- `event`: System events (phx_*) vs custom events
- `payload`: Must be a JSON object, never a primitive

### ✅ 1.2.1.3 Add convenience constructors for common message types

Implemented 5 constructor functions:

#### 1. `init()` - Generic message constructor
```zig
pub fn init(
    allocator: std.mem.Allocator,
    topic: []const u8,
    event: []const u8,
    payload: std.json.Value,
) PhoenixMessage
```
- Creates a message with null `join_ref` and `ref`
- Used as base for custom messages

#### 2. `initJoin()` - Join message constructor
```zig
pub fn initJoin(
    allocator: std.mem.Allocator,
    topic: []const u8,
    join_ref: []const u8,
    payload: std.json.Value,
) PhoenixMessage
```
- Automatically sets event to "phx_join"
- Sets both `join_ref` and `ref` to the same value (Phoenix convention)
- Used for subscribing to channels

#### 3. `initLeave()` - Leave message constructor
```zig
pub fn initLeave(
    allocator: std.mem.Allocator,
    topic: []const u8,
    ref: []const u8,
    payload: std.json.Value,
) PhoenixMessage
```
- Automatically sets event to "phx_leave"
- Sets `join_ref` to null
- Used for unsubscribing from channels

#### 4. `initHeartbeat()` - Heartbeat message constructor
```zig
pub fn initHeartbeat(
    allocator: std.mem.Allocator,
    ref: []const u8,
    payload: std.json.Value,
) PhoenixMessage
```
- Automatically sets topic to "phoenix" (reserved topic)
- Automatically sets event to "heartbeat"
- Sets `join_ref` to null
- Used for connection keepalive

#### 5. `initEvent()` - Custom event message constructor
```zig
pub fn initEvent(
    allocator: std.mem.Allocator,
    topic: []const u8,
    event: []const u8,
    ref: []const u8,
    payload: std.json.Value,
) PhoenixMessage
```
- Allows custom topic and event names
- Sets `join_ref` to null
- Used for user-defined events

#### Helper: `emptyPayload()` - Create empty JSON object
```zig
pub fn emptyPayload(allocator: std.mem.Allocator) !std.json.Value
```
- Creates an empty JSON object `{}`
- Useful for messages that don't need payload data
- Must be deinitialized by caller

### ✅ 1.2.1.4 Implement deinit() for proper memory cleanup

```zig
pub fn deinit(self: *PhoenixMessage) void
```

**Memory Management Strategy:**
- **Payload ownership**: Caller is responsible for payload cleanup
- **Rationale**: Payloads may be shared, borrowed, or owned
- **Documentation**: Clear doc comments explain ownership model
- **Pattern**: Follows Zig conventions for flexible ownership

**Usage Pattern:**
```zig
var payload = try PhoenixMessage.emptyPayload(allocator);
defer payload.object.deinit(); // Caller owns payload

var message = PhoenixMessage.init(allocator, "topic", "event", payload);
defer message.deinit();
```
